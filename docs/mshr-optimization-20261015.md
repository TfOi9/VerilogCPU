# 双 MSHR 与同一行合并优化结果

相对 `2a34e20`，本轮两项 MSHR 将 vvadd 从 **8,361 降到 5,956 周期**，IPC 提升 **40.38%**；六项 IPC 几何平均从 **0.730564 提升到 0.788517**（**+7.93%**），六项均有收益。官方综合总面积增加 **1.20%**，估计频率提升 **3.55%**。保留无争用 Load 命中三周期、原 LSQ/完成网络快速返回及 Store 证明机制。

## 实现

两项 MSHR 独立保存完整行地址、victim、读写 sent/done/error 与 refill 数据；每行最多合并四笔请求。FIFO 保存 CPU ID 和完整 ROB tag，Store 按字节掩码修改缓冲，后续同一行 Load 读取修改后的值。两个不同 set 的 miss 可并行；同 set 的不同行仍保守串行，以保持替换与不可失败 Store 的所有权。

桥接为每个读 owner FIFO 槽和独立写 owner 保存 MSHR ID，返回 ID 与读写类型共同关联事务。MSHR 等自身 refill 与脏写回都结束后再返回；任一错误只影响本项 waiter。写回失败保留 dirty victim；写回成功、refill 失败保留 clean victim。已完成的 MSHR 轮转共享返回和单端口 refill 安装，避免覆盖或重复安装。模块结构、接线和时序详见 [dcache-mshr.md](dcache-mshr.md)。

首次 qsort 暴露了合并返回暂停期间的 S1 SRAM 停读问题：FakeRAM 禁用后读输出未定义，恢复时可能使已证明 Store 丢失 tag。修复为所有不安装的周期持续读取 S1，安装后重读并刷新元数据。原始失败和定位快照保留；专门的定向负对照关闭此修复后必须触发保护断言。

## IPC 与 PPA

两侧均为 FE2/BE2、PRF64、ROB32、RECOVERY4、Icache 1 KiB/1 way、Dcache 16 KiB/2 ways、Store 目录 128 项、后续命中确认开启，官方外部主存延迟 10 周期。基线为单项 MSHR，本轮为两项，未扩大 LSQ 或执行宽度。

| multiply | 19,934 | 19,447 | +2.50% |
| qsort | 198,351 | 197,268 | +0.55% |

| towers | 7,802 | 7,789 | +0.17% |

| IPC 几何平均 | 0.7305642603 | 0.7885169658 | +7.93% |
| 总面积 (um²) | 30,699.1324 | 31,068.2689 | +1.20% |

IPC/面积提升 **6.65%**；以 `IPC × Fmax` 估算的吞吐提升 **11.76%**。官方 `opt` 使用未修改的框架、Yosys 0.63、ASAP7 RVT TT、OpenSTA，驱动单元 `INVx1_ASAP7_75t_R`、负载 5 fF、目标 2 ns。该目标下 setup slack 仍为 **-0.836805 ns**；频率是理想时钟、无互连寄生的 STA 估计，尚未布局布线签核，也未测量功耗。

最高档要求同一配置 IPC≥1.0985、面积≤36,000 um²、频率≥300 MHz；当前仍未达到联合门槛，限制项是 IPC。

官方全局关键路径为 `core.lsq.address[1][1] → core.lsq.report_sent[0]`，最坏到达时间 2.782 ns。pre-ABC 重放按保留 DFF 身份关联起终点，并核验官方 PPA 文件未改变。

## vvadd 的收益来源

插桩运行的六项周期均与官方未插桩运行一致。将同一新 RTL 配置回单项 MSHR 后，六项周期及全部 profile 计数与旧基线完全一致，可排除桥接请求锁定调整等伴随改动对这些结果的影响。

| vvadd 计数 | 单项 | 两项 |
| --- | ---: | ---: |
| refill 请求/安装 | 300 / 300 | 300 / 300 |
| 合并请求 | 0 | 334 |
| 两项 MSHR 同时占用的周期 | 0 | 1,344 |
| 桥内两个 D 读同时在途的周期 | 0 | 1,185 |
| 第二笔 miss 被阻塞的周期 | 2,668 | 1,166 |
| S1 set 锁定周期 | 1,314 | 0 |
| Load 请求至返回消费平均周期 | 13.54 | 11.81 |
| Store 请求至返回消费平均周期 | 13.69 | 9.49 |

收益来自重叠 miss 和解除同一行的前端阻塞，外部 refill 数量未减少。合并请求原先会等待先前 refill 后再作为命中处理；本轮提前加入 MSHR，不会为它们额外读取主存。上述请求延迟包含返回消费时钟，和 cache 的三周期命中口径不同。

两项 MSHR、四项 LSQ 请求槽、同 set 替换和单端口 refill 仍有容量或仲裁限制，因此第二笔 miss 阻塞未完全消失。

## 验证与复现

最终验收全部通过：

- 25 个官方程序；六项性能程序与插桩周期逐项一致。
- 完整 `make unit`、`make lint`、HUM 和返回归属回归。
- 99 组 MSHR 专项配置，包括 57,068 次 cache 返回检查、776 次桥接返回检查和三个必须拒绝的负对照；覆盖三周期命中、掩码顺序、双完成、两种读写返回顺序和错误。原 LSQ/完成网络的快速返回测试随完整单元套件通过。
- 81 组参数矩阵的 324 项静态检查、九组代表配置的 243 次程序运行和 27 条退休轨迹对照。
- 64 组 Store 后续确认、71 组目录、28 项 HUM/错误/回压回归及 12,550 次返回边界检查。
- 当前 RTL 与官方快照及完整回归输入一致，PPA、程序、profile 和诊断日志哈希核验通过；新 RTL 配回单项 MSHR 后的六项周期及 profile 计数与旧基线完全一致。

原始证据位于 `build/mshr-20261015/`，最终输入与日志哈希见 [results-summary.json](../experiments/mshr_20261015/results-summary.json)。单元测试、完整矩阵、官方测量和插桩命令见 [实验说明](../experiments/mshr_20261015/README.md)。汇总工具核对当前 RTL 与官方快照一致，并要求完整回归通过后才生成成功报告。
