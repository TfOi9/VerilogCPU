# 六程序性能瓶颈调查（2026-10-14）

当前达到 IPC > 1.0985 需要结构性优化。正式核心的大 Cache 配置六程序几何平均为 **0.547700**，还需 **2.0057 倍吞吐**。本轮测得最好的 4×4 配置也只有 **0.586545**。优先方向是普通 Store 排队提交、缩短结果到消费者的延迟、非阻塞访存，以及分支预测与正确路径恢复的协同改进。

本轮没有修改正式 RTL，没有运行新综合。调查基于 `e5526dd`，新增计数器、冻结副本中的参数对照和通用依赖链微基准。完成 12 组配置 × 全部 6 个官方性能程序 = **72 次运行**，以及 **5 个独立解释器核对结果与退休数量的微基准**。这不是对各候选的完整正确性验收；上一轮正式核心的完整回归见 [optimization-20261014.md](optimization-20261014.md)。

## 1. 测量口径与当前基线

除标注的单因素对照外，固定 FE=BE=2、PRF64、ROB32、LSQ8、回滚宽度 4、外存延迟 10 周期。默认 Cache 为 I 1 KiB / D 4 KiB、直接映射；大 Cache 为 I 2 KiB / D 16 KiB、D 两路。IPC 使用官方 `metrics.json` 的动态指令数除以总周期，六程序等权取几何平均。

| 程序 | 默认 Cache IPC | 大 Cache IPC | 大 Cache 周期 | 队首 Store 等响应 | 队首 Load 未完成 | ROB 恢复 | 有退休的周期 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| median | 0.391199 | 0.418279 | 16,642 | 27.31% | 14.65% | 14.08% | 27.03% |
| multiply | 0.911808 | 0.911808 | 23,823 | 6.70% | 4.78% | 6.57% | 49.83% |
| qsort | 0.378718 | 0.522783 | 267,606 | 23.11% | 18.74% | 15.98% | 32.91% |
| rsort | 0.282893 | 0.653885 | 299,317 | 58.64% | 5.70% | 0.01% | 35.44% |
| towers | 0.439870 | 0.440678 | 11,977 | 62.90% | 2.30% | 1.29% | 27.09% |
| vvadd | 0.423160 | 0.469831 | 9,629 | 60.54% | 12.04% | 0.10% | 25.11% |
| **几何平均** | **0.438542** | **0.547700** | — | — | — | — | — |

百分比均以**总周期**为分母。无退休时根据 ROB 状态进行互斥分类，另有 Store 地址未完成、分支未完成、其他队首未完成、ROB 空等分类，故表中几列并非全部分类。存在退休时归入“有退休”，不再归入某一种等待。全部分类之和已逐例核对等于总周期。

Store 等响应类包含请求准备、排队和 Cache 处理，不能当成外存延迟。分支完成事件可能位于随后被取消的推测路径，不能作为退休分支准确率。资源满、队列中存在依赖 Load、Cache 非 RUN 等统计会重叠，也不等于这些资源导致的独占停顿。

本轮默认及大 Cache 的 **12 项周期和上一轮共有计数器全部复现**，新增观测没有改变这些程序的测量结果。当前六程序均值不能与早先三程序的 0.6566 直接比较。

## 2. 参数对照：哪些简单扩容有效

### Cache 单独控制

| I Cache | D Cache | 六程序 IPC 几何平均 |
| --- | --- | ---: |
| 1 KiB | 4 KiB 直接映射 | 0.438542 |
| 1 KiB | 4 KiB 两路 | 0.465310 |
| 1 KiB | 8 KiB 两路 | 0.500201 |
| 1 KiB | 16 KiB 两路 | 0.547532 |
| 2 KiB | 16 KiB 两路 | 0.547700 |

D 容量和冲突仍然重要；I 从 1 KiB 扩到 2 KiB 仅使 towers 少 22 周期，其余五项完全不变，均值提升 **0.0306%**。下一轮可用 I 1 KiB / D 16 KiB 两路作为性能开发起点；其 PPA 尚未测量，不能直接认定面积或时序达标。

### 在大 Cache 基础上的单因素对照

| 改动 | 六程序 IPC 几何平均 | 相对大 Cache 基线 |
| --- | ---: | ---: |
| 基线 2×2、PRF64、ROB32、LSQ8、恢复宽度 4 | 0.547700 | — |
| PRF96 / ROB64 | 0.548647 | +0.173% |
| LSQ16 | 0.548670 | +0.177% |
| 恢复宽度 8 | 0.548566 | +0.158% |
| BHT256 / BTB64 | 0.548424 | +0.132% |
| FE4 / BE2 | 0.553300 | +1.023% |
| FE2 / BE4 | 0.579688 | +5.840% |
| FE4 / BE4 | 0.586545 | +7.092% |

这里 BHT/BTB 和 PRF/ROB 各自是成组参数，不能进一步归因到组内某一个资源。BE 同时影响后端发射、完成和退休等通路，也不能把 FE2/BE4 的收益只归因于更多 ALU。

在排除全局暂停的活跃周期中，rsort 的 ROB 满占 45.43%、vvadd 占 59.95%，towers 的 LSQ 满占 56.95%；但扩大窗口收益很小。它们主要提示退休受阻造成资源积压，而非证明容量是根因。六程序均未出现物理寄存器空闲表耗尽。INT RS 满最高为 multiply 的 6.88%；写回源反压最高为 median 的 1.96%。当前首先要解决的是延迟与串行约束，写回总带宽不是已经证实的主瓶颈。

## 3. 通用依赖链微基准

每个循环执行 64 个主体操作、重复 200 次，共 12,800 个主体操作；另含初始化、循环控制和退出。五项均只发生一次 D refill，使用相同大 Cache 的 2×2 模拟器，结果由独立架构解释器核对。

| 微基准 | 周期 | IPC | 暴露的限制 |
| --- | ---: | ---: | --- |
| 单条 ALU 依赖链 | 25,965 | 0.508723 | 主体平均约 2 周期/操作 |
| 四条独立 ALU 链 | 7,303 | 1.809120 | 双发射在依赖较少时能接近满利用 |
| 地址依赖的连续 Load | 102,507 | 0.128869 | 热 Cache 仍约 8 周期/操作 |
| 独立 Load | 14,842 | 0.889974 | 单 Load 地址生成和返回通路的吞吐限制 |
| 连续热 Store | 64,375 | 0.205188 | 仍约 5 周期/操作 |

这些是包含循环开销的端到端测量，不是精确的单模块流水级延迟，也不是对六程序收益的预测。它们明确说明：仅改善命中率不能消除核心内部的数据传递与确认延迟。

另一个容易误判的点是：六个官方性能程序的**退休 MUL/DIV 指令均为零**。`perf_multiply` 实际执行移位、加法和条件分支实现的软件乘法。因此，为本轮性能目标优化乘法器吞吐并无直接证据支持。

## 4. 七条深入优化方向

### 方向一：建立普通 RAM Store 的两阶段提交协议（最高优先级）

**证据。** Store 等响应占 towers 62.90%、vvadd 60.54%、rsort 58.64%。其中 towers 同时处于 D-Cache 非 RUN 的周期仅占总周期 4.58%，说明其主要损失并非缺失；qsort 的对应交集也仅 0.97%。热 Store 微基准约 5 周期/笔。

| 程序 | Store 请求准备 | Store 请求排队 | Store 已请求、等完成 | Store 队首且 D-Cache 非 RUN |
| --- | ---: | ---: | ---: | ---: |
| median | 2.28% | 6.24% | 18.79% | 15.76% |
| multiply | 0.44% | 0.45% | 5.81% | 4.31% |
| qsort | 2.95% | 5.17% | 14.99% | 0.97% |
| rsort | 4.80% | 11.27% | 42.57% | 15.25% |
| towers | 4.13% | 13.53% | 45.24% | 4.58% |
| vvadd | 3.13% | 16.99% | 40.42% | 44.80% |

前三列互斥并合计为 Store 等响应类；最后一列是交集，不能再相加。LSQ 的 `write_requested` 在请求寄存器装入时置位，分类先检查排队请求，再计剩余在途项。源码锚点：[LSQ 提交条件](../rtl/rv32_load_store_queue.v#L500)、[请求准备](../rtl/rv32_load_store_queue.v#L532)。

**设计。** 将地址/权限与对齐检查、Cache 探测、需要的 refill 和错误确认提前进行；当普通 RAM Store 已进入不会再出现需精确归属错误的状态，允许进入已提交 Store buffer，随后依序排队更新 Cache。连续 Store 的退休不再逐笔等待完整请求往返。先定义协议和可证明的不变量，再实现小容量缓冲；不能只提前置 `commit_ready`。

**关键约束。** 提前探测后到实际写入前，Cache 行的替换与所有权必须得到保护或重新验证；所有可能失败且需精确报告的操作必须在退休前处理。已提交写不能被分支回滚清除，后续 Load 必须从 Store buffer 按最新字节转发；脏行替换、同址写合并、Cache 错误和反压仍须有明确归属。MMIO 保持队首发出并等待响应。若现有错误接口不允许证明这个边界，应先做安全的提前准备/预取与同拍衔接，保留响应后退休。

**验证。** 热 Store、Store→Load 同址和部分字节、跨行访问、替换冲突、错误注入、回滚与已提交写并发、MMIO 前序 RAM 写排空；随后重点看 towers/rsort/vvadd 和全六项。上一轮仅提前下一笔请求的候选曾使 qsort 回退，不能把微基准收益直接推广。

### 方向二：缩短 ALU/Load 结果到消费者的路径（最高优先级）

**证据。** ALU 单链 0.509 IPC、独立链 1.809 IPC，说明存在可观的依赖延迟。热 Load 依赖链只有 0.129 IPC。大 Cache 下 median 有 5.62%、qsort 有 5.13% 的总周期处于“队首 Load 已 report_sent、ROB 仍未完成”，而写回反压仅约 1%–2%。这支持优先调查流水级与唤醒路径，而非单纯增加写回端口。

**设计。** 当前 [ALU 注册结果](../rtl/rv32i_alu.v#L239) 后又进入 [写回源缓冲](../rtl/rv32_completion_writeback_network.v#L333)，广播依赖 [ROB 接收和目的寄存器确认](../rtl/rv32_completion_writeback_network.v#L246)。可评估执行结果直接旁路到 RS、PRF 就绪表和分支操作数；随执行请求携带已验证的物理目的寄存器与代际标签，减少结果再次经 ROB 查询的组合路径。Load 在错误检查和标签确认后尽早转发，减少 LSQ 返回、源缓冲和唤醒之间的等待。

**关键约束。** 保持 SPEC 要求的 Cache 3 周期命中延迟；优化其外围队列与旁路。提前唤醒必须处理取消、物理寄存器复用、异常 Load、重复结果和源反压。不要为了减少一拍重新引入贯穿 ALU、ROB、写回、RS 选择的长组合路径；需要同时验证 ≥300 MHz 的时序。

**验证。** ALU→ALU、Load→ALU、Load→地址、ALU→分支、同周期同目的寄存器、回滚后的迟到结果；以依赖链和完整退休差分证明正确性，并重测六程序。

### 方向三：从阻塞式 D-Cache 走向命中继续处理、多行在途（高优先级）

**证据。** 当前 [D-Cache 请求 ready](../rtl/rv32_l1_data_cache.v#L169) 在 miss 时关闭，脏行写回和 refill 串行执行；[桥接仲裁器](../rtl/rv32_l1_cache_axi_bridge.v#L43) 只有一个行事务所有者。LSQ 的四笔在途不是四个并行 miss。

**设计。** 第一阶段加入脏行写回缓冲并支持 hit-under-miss；第二阶段增加 2–4 项 MSHR/行事务队列，对同一行缺失合并。同步扩展桥接器的请求关联与响应分发，避免仅扩大 LSQ 在途上限。现有 AXI 适配器**已能流水发出同一 16 B 行的四个 32 位请求**；缺口是跨行事务与 Cache 服务并行，而非重新实现已经存在的字级流水。

**关键约束。** Cache SRAM 单端口的读写冲突、同组替换、脏 victim 的持有、响应有序性或显式标签、错误响应精确归属、回滚请求排空均需一起设计。允许乱序响应时尤其要改变 LSQ 当前的关联假设。Store 提交改进后会增加 Cache 写压力，此方向需要联测。

**验证。** 独立多行 Load、一个 miss 配合其他行 hit、脏替换与 refill 并发、同一行请求合并、I/D 同时争用、总线随机反压与错误注入；记录实际并行 miss 数和被隐藏的等待，不能只看队列占用。

### 方向四：降低冷缺失和流式访问的有效代价（高优先级）

**证据。** 默认→大 Cache 的 refill/脏写回分别为：qsort 5,395/1,048→1,037/12，rsort 15,849/7,950→2,322/1,116，容量收益明确。但 vvadd 的 **300 次 refill 完全不变**，大 Cache 的 D 非 RUN 达 **62.69%** 总周期；median 的 **302 次 refill 也不变**。这部分需要从访问流和返回延迟着手，不能期待继续扩容同样有效。

**设计。** 增加逐行地址统计，先确认唯一行数、复用距离和冷/冲突缺失，再比较通用 next-line/stride 预取、关键字优先返回，以及完整覆盖一行时的 Store 合并/免读分配。也可评估 32/64 B 行的空间复用，但这涉及 Cache、桥接接口和 FakeRAM 形状调整，且增大无效传输。

**关键约束。** 预取只能是无架构副作用的普通 RAM 请求；错误不能作为程序异常提交，MMIO 不预取。需求请求优先，限制带宽与污染。关键字提前返回需要明确该字错误与整行后续错误的接口语义。当前仅由容量不敏感和程序结构提示冷/流式限制，尚未逐 miss 证明全部为冷缺失，不能把“不变的 refill 数”等同于完整的冷缺失分类。

**验证。** 顺序、跨步、随机、部分行写、读写交替和跨页/地址边界；统计有效预取率、额外流量、脏写回、需求延迟及全六项变化。策略不得依赖某个测试点名称或固定 PC。

### 方向五：改善条件分支预测与提前解析（中高优先级）

**证据。** qsort 接收的控制流完成中，条件分支 42,586 次、预测下一 PC 不符 10,839 次；JAL 不符 0 次、JALR 不符 4 次。median 对应条件不符 564 次，multiply 为 665 次。分支事件计数包含推测路径，不能把这些比值当成退休准确率，但足以表明当前 qsort 重点是条件分支。BHT256/BTB64 的全六项收益仅 **0.132%**。

**设计。** 先加入逐 PC 的方向/目标错误、表冲突、更新时机及被取消分支统计，区分 Bimodal 索引别名和分支本身的模式难度。评估低成本索引/布局、BTB 组相联或控制流类型分离；结合方向二，让分支操作数更早可用并及时获得执行机会。若以后扩展预测算法，需要明确这是超出当前简单 Bimodal 设计的候选，不能以扩大表项替代对模式的诊断。

**关键约束。** 当前 [预测器](../rtl/rv32_branch_predictor.v#L42) 为 BHT64/BTB16；早期取指使用 BTB，取回指令后的条件分支/JAL 可直接计算目标，两个阶段要分开观察。前端返回时的路径修正与执行端架构误预测必须分别计数。RAS 可针对返回错误优化，但当前六项 JALR 错误数量有限，不列为首要方案。

**验证。** 固定方向、交替/相关方向、索引冲突、嵌套调用/返回、回滚时预测器更新；记录退休分支错误与推测分支事件，分别报告次数、每次代价和整体 IPC。

### 方向六：把快速恢复与正确路径供给一起设计（中高优先级）

**证据。** qsort 回滚宽度 4→8：

| 指标 | 宽度 4 | 宽度 8 |
| --- | ---: | ---: |
| 总周期 | 267,606 | 266,555 |
| ROB 恢复周期 | 42,774 | 24,316 |
| 恢复事件 | 10,766 | 10,740 |
| 回滚项数 | 156,294 | 155,869 |
| ROB 空周期 | 8,327 | 18,898 |
| 队首 Load 未完成周期 | 50,156 | 54,270 |
| 队首分支未完成周期 | 9,661 | 10,854 |

恢复周期减少 18,458，总周期却只减少 1,051。更快恢复暴露了更多正确路径供给/依赖等待，分类随时间重叠关系变化；这不是“恢复缩短了多少就一定节省多少”。

**设计。** 评估 RAT/空闲表检查点、按代际取消错误路径，使恢复不再完全依赖逐项扫描；允许安全的较老指令继续完成。同时在确定重定向目标后尽早启动取指，优化旧响应取消、目标行缓存或取指行缓冲。当前 [取指返回拆包](../rtl/rv32_fetch_pipeline.v#L338) 每次最多取 FE_WIDTH 条，FE2 只能消费 16 B 行的一部分；保留行内剩余指令或预译码可减少重复取行及跳转处气泡。单独 FE4 的均值收益只有 1.023%，也说明不能只扩宽入口。

**关键约束。** 恢复期间当前 [pipeline_hold](../rtl/rv32_cpu_core.v#L269) 会暂停后端，解除它要明确较老指令集合、ROB 环形年龄比较、分支/异常优先级、PRF 释放和旧响应代际隔离。检查点需要面积和多分支恢复预算。不要把 ROB 空全部解释成 I-Cache miss；I 扩容实验已经表明容量不是当前主要供给问题。

**验证。** 深浅回滚、嵌套误预测、回滚同时较老 Load 返回/Store 提交、跨 ROB 回绕、目标行 miss，以及恢复期间第二个异常；观察从重定向到首条正确路径退休的完整延迟分布。

### 方向七：在等待降低后重新平衡后端宽度与物理实现（后续优先级）

**证据。** FE2/BE4 提升 5.840%，FE4/BE4 提升 7.092%，说明后端扩宽并非没有价值；但当前不足以接近目标，而且候选没有新 PPA。PRF96/ROB64、LSQ16 的均值收益均低于 0.2%。保守的 Load/Store 依赖判断也并非已证实的首要限制：有候选 Load 被 Store 依赖规则阻挡的周期最高仅为 qsort 的 2.52% 活跃周期，现阶段不优先加入高复杂度内存依赖预测。

**设计。** 先解除 Store、结果依赖和 miss 串行，再重新做 FE/BE、完成宽度、Load 地址生成端口、RS/LSQ 容量敏感度。维持树形选择器，检查高扇出控制、无效 payload 清零以及旁路广播负载；在证明无效数据不可观察后，可减少无效槽位的大范围写使能。以新的关键路径决定是否做分层广播、局部仲裁，而非预设所有资源翻倍。

**验证。** 每次有效组合跑六程序、退休差分和参数矩阵，再用相同 ASAP7/FakeRAM 流程测面积与时序，避免把 IPC 提升换成低频。

## 5. 联合目标与实施顺序

上一轮与当前正式 RTL 哈希一致的 PPA 为：默认 Cache **24,994.60 µm² / 300.38 MHz**，大 Cache **32,054.58 µm² / 292.66 MHz**。这是 TT、理想时钟、无布线寄生/CTS 的估计值，本轮没有重跑。大 Cache 距离 36,000 µm² 仅约 3,945 µm² 余量，且估计频率已低于 300 MHz。不能把不同 Cache 配置的 IPC 和频率拼接成联合达标。

作为优先级的辅助检查，若机械删除现有大 Cache 的全部 Store 等响应分类、其余周期保持不变，六程序均值为 **0.9742**；再删除 Load 等待分类才到 **1.1767**。同时删除 Store 与恢复分类为 **1.0695**。这些只是固定周期账目的反事实计算，**不是可实现收益、预测或严格架构上界**；实际优化会改变等待重叠、推测深度和分类。它们提示需要跨多个瓶颈协同验证，不能据此保证某组合达到目标。

建议顺序：

1. **先做普通 Store 提交协议和 ALU/Load 早旁路两个独立设计。** 以 Store 热循环、依赖链、towers/rsort/median 为初筛，然后必须跑全六项；先验证安全边界和收益来源。
2. **在有效改动上做 D-Cache 并行化与流式延迟优化。** 使用 I 1 KiB / D 16 KiB 两路作候选基线，并补同版本 PPA；限制缓冲和 MSHR 数量。
3. **随后联合改善条件分支、恢复和重定向后的供给。** 重点 qsort，同时防止 multiply/median 回退；逐 PC 分支和逐行 miss 分类是当前还缺的诊断证据。
4. **最后重新扫宽度和容量，做完整验收。** 六项几何平均 >1.0985 与面积≤36,000 µm²、频率≥300 MHz 必须在同一版本、同一配置下成立。当前结果尚未证明可达，也没有证明不可达。

## 6. 复现与审计边界

脚本及精确命令见 [experiments/bottlenecks_20261014/README.md](../experiments/bottlenecks_20261014/README.md)，机器可读证据见 [results-summary.json](../experiments/bottlenecks_20261014/results-summary.json)。原始输出位于 `build/bottlenecks-20261014/`：

- `profile-v2/`：默认、大 Cache；12 项。
- `sensitivity/`：8 组参数对照；48 项。
- `width-isolation/`：前后端独立宽度；12 项。
- `probes/`：5 个通用微基准。
- `profile/`：第一次构建未开启 `--trace`，与官方 harness 的 VCD 链接不匹配；这是工具构建错误，未运行性能程序，保留失败日志。修正后以上运行全部通过。

构建每次 timeout 360 秒、2 个编译作业；每个程序 timeout 30 秒，官方性能运行上限 300 万周期。审计脚本核对模拟器/冻结源码/执行脚本/日志哈希、正式 RTL 不变、快照仅有声明的 LSQ/预测器改动、各直方图与互斥分类计数、退休数，以及上一轮基线复现。原始运行中的外部程序镜像与官方 harness 没有全部纳入运行前后哈希守卫；汇总明确将这部分哈希标成“报告时记录”，冻结 harness 与当前官方源码加观测替换完全一致，避免夸大溯源范围。

新增候选只跑了全套性能程序和其中的结果检查，**没有重新跑全部正确性程序、全部参数矩阵或新综合**。后续集成任何候选之前仍需这些门槛。正式 RTL、SORA 和既有未提交计划文件均未修改。
